## 1. Цель

Собрать полуавтоматический пайплайн реверс-инжиниринга, поставляемый как **плагин для Claude Code**. Claude выступает оркестратором готовых инструментов (Ghidra, x64dbg, Frida, angr и др.), детерминированную работу выполняют сами инструменты, а быстрый нативный слой (триаж, эмуляция, патчинг) реализуется на **Rust** в виде MCP-сервера.

Пайплайн — **тонкая обвязка** над существующими инструментами, а не собственный движок анализа. Готовые решения (binary-mcp, revula, Kong) подключаются как бэкенды, а не переписываются.

### 1.1. Форма поставки

Продукт — это **плагин Claude Code**, то есть папка с манифестом и компонентами, устанавливаемая через marketplace (`/plugin install`). Плагин сам по себе не компилируемая программа: это JSON-манифест плюс markdown-компоненты. Rust живёт **внутри** плагина как бэкенд, который вызывают его компоненты.

Состав плагина:
- `.claude-plugin/plugin.json` — обязательный манифест.
- `skills/*/SKILL.md` — skills по этапам пайплайна (markdown).
- `commands/*.md` — слэш-команды (markdown).
- `hooks/hooks.json` — хуки (опционально).
- `.mcp.json` — декларация MCP-серверов, в т.ч. собственного Rust-сервера.
- `bin/` — скомпилированный Rust MCP-сервер и вспомогательные бинарники.

Связь: skills и hooks вызывают Rust-бинарь; `.mcp.json` объявляет Rust MCP-сервер как источник инструментов Claude. Для переносимых путей использовать `${CLAUDE_PLUGIN_ROOT}`.

### 1.2. Нефункциональные принципы

- **Изоляция прежде всего.** Исполнение образцов строго в виртуальной машине; на хосте только статика.
- **Воспроизводимость.** Каждый анализ оформляется как кейс с артефактами и заметками, переживающими перезапуск.
- **Верификация.** Любая гипотеза из статики подтверждается в динамике перед записью в итог.
- **Подключаемость.** Инструменты деобфускации и динамики — сменные модули, выбираемые по типу цели и защиты.
- **Разделение слоёв.** На Rust пишется только то, что нативно; тяжёлые движки (Ghidra, angr, Frida) оркестрируются снаружи, а не переписываются.

## 2. Область применения

### 2.1. Основная цель анализа

- **Приоритет 1:** исполняемые файлы Windows (PE: `.exe`, `.dll`), архитектуры x86 и x86-64.
- Прочие форматы (ELF, APK, прошивки) — вне первой версии; закладывается расширяемость, но не реализуется.

### 2.2. Профили анализа

Этапы одинаковые; различаются выход и строгость изоляции. Профиль задаётся одним параметром при создании кейса.

| Профиль | Назначение | Доп. инструменты | Артефакты на выходе |
|---|---|---|---|
| `understand` | Понять логику программы | — | Описание логики, имена функций, схема протокола/формата |
| `malware` | Разбор вредоносных образцов | capa, YARA, фейковая сеть, строгая изоляция | Отчёт о поведении, IOC, YARA-правила |
| `vuln` | Поиск уязвимостей, диффинг патчей | ghidriff, поиск опасных конструкций | Список подозрительных функций с доказательствами |
| `ctf` | CTF и восстановление совместимости | angr, unicorn (упор на скорость) | Решение задачи или рабочий парсер формата |

> Профили `ctf` и `compat` (совместимость) объединены: набор инструментов совпадает.

### 2.3. Среда

- **Хост:** Windows.
- **Изоляция:** отдельная виртуальная машина Windows со снимком. x64dbg работает нативно внутри VM.
- Отдельная Linux-VM в первой версии не требуется.

### 2.4. Режим работы

**Гибридный.**

- **Автоматическая часть** (без участия пользователя): триаж, **статическая** распаковка, headless-статика, первичное именование, расшифровка строк эмуляцией диапазона, черновой отчёт.
- **Интерактивная часть** (пользователь + Claude): уточнение имён и типов, гипотезы, написание хуков, запуск динамики по явной команде.

## 3. Этапы пайплайна

Порядок обязателен. Возможен возврат назад (например, после распаковки — повторный триаж).

### Этап 0. Изоляция и создание кейса
- Хэши образца (MD5, SHA-1, SHA-256).
- Создать структуру кейса (раздел 7).
- Оригинал в `sample/` в режиме «только чтение».
- Убедиться, что активен снимок VM и сеть в нужном режиме (для `malware` — выключена/фейковая).
- **Роль Claude:** создать скелет кейса и заготовку `notes.md`.

### Этап 1. Триаж
- Формат, архитектура, секции, импорты, энтропия (LIEF).
- Детект упаковщика/протектора (DIE).
- Детект возможностей и поведения (capa).
- Прогон YARA-правил.
- Результат в `artifacts/triage.json`.
- **Роль Claude:** прочитать `triage.json`, выбрать маршрут и инструменты.
- **Слой:** основной кандидат на реализацию в Rust MCP-сервере (см. 5.2).

### Этап 2. Распаковка (если упаковано)
- Только при признаках упаковки из этапа 1.
- **Статическая распаковка** (известный упаковщик, напр. UPX) — автоматически на хосте.
- **Дамп из памяти** (Frida или x64dbg в VM), поиск OEP — это исполнение образца, поэтому **только внутри VM и по команде пользователя** (как этап 5), не в автоматической части.
- **После распаковки — вернуться на этап 1** для повторного триажа.
- **Роль Claude:** написать скрипт хуков/дампа, разобрать результат.

### Этап 3. Статика
- Headless-анализ в Ghidra (`analyzeHeadless`), экспорт функций, строк, xrefs.
- Опционально: Kong для массового именования и типизации.
- **Роль Claude:** через ReVa/MCP переименовывать функции и переменные, восстанавливать типы, формулировать гипотезы.

### Этап 4. Деобфускация (подключаемый модуль по типу защиты)
Для OLLVM-подобных защит порядок: сначала opaque predicates, затем unflatten, затем MBA.

| Тип защиты | Инструмент |
|---|---|
| Control Flow Flattening (CFF) | angr |
| Bogus Control Flow (BCF) | angr |
| Instruction Substitution / MBA | упрощение выражений, в конце цепочки |
| Шифрование строк | unicorn (эмуляция расшифровщика) |
| VM-протекторы (VMProtect, Themida) | **ручная работа**, Claude только ассистирует |

- Kong может выступать как LLM-слой деобфускации поверх вывода декомпилятора.
- **Роль Claude:** определить тип защиты, написать скрипты под инструмент.

### Этап 5. Динамика
- Трассировка и хуки (Frida), ручная отладка и обход anti-debug (x64dbg).
- **Только внутри VM и только по явной команде пользователя.**
- **Роль Claude:** написать скрипты, разобрать логи.

### Этап 6. Верификация
- Сопоставить гипотезы из статики с реальной трассой из динамики.
- Зафиксировать только подтверждённое в `notes.md`.
- Записать уточнённые имена/типы обратно в базу Ghidra (writeback).
- **Роль Claude:** сверка гипотез с трассой, фиксация результата.

### Этап 7. Выход
- Патчинг при необходимости (keystone + LIEF).
- Генерация артефактов по профилю: `report.md`, YARA-правила, IOC, парсер формата.
- **Роль Claude:** собрать итоговые артефакты.

## 4. Изоляция и модель угроз

Критическое требование: среди целей есть вредоносные образцы. Недоверенным является **не только исполнение** образца, но и его **содержимое**, которое читает Claude (см. 4.4).

### 4.1. Границы исполнения

- **Хост:** только статика. Ghidra, разбор PE, capa, Claude с MCP, Rust-бэкенд триажа. Образец **никогда** не исполняется на хосте.
- **VM:** всё, что исполняет код образца (x64dbg, Frida, запуск образца, дамп из памяти).
  - Снимок до запуска, откат после анализа.
  - Сеть выключена или заведена на фейковую — **FakeNet-NG внутри Windows-VM** (INetSim требует Linux-VM, которой в первой версии нет). Обязательно для `malware`.
  - Общий буфер обмена и общие папки отключены.
- **Пограничный случай — эмуляция и символьное исполнение (unicorn, angr) на хосте.** Формально это тоже исполнение кода образца. Разрешено только на выбранном диапазоне (расшифровщик строк, одна функция), с лимитом шагов и памяти, без доступа к реальным системным вызовам. Запуск **всего** образца в эмуляторе на хосте запрещён.

### 4.2. Передача файлов между хостом и VM

Односторонний канал «из VM на хост» недостаточен: образец и скрипты хуков нужно сначала доставить **в** VM.

- **`malware`:** перенос только вручную, через носитель/папку, подключаемые к VM разово и не смонтированные на хосте во время исполнения. Автоматического канала хост→VM нет.
- **`understand`, `ctf`:** допустима выделенная сеть только хост↔VM, где файрвол VM разрешает **входящие** с хоста на порт Frida и блокирует **любой исходящий** трафик из VM. Claude управляет Frida через этот порт, но сессию инициирует пользователь.

### 4.3. Механизмы на хосте (а не только правила)

Плагин не может навязать Claude режим разрешений: в его `settings.json` действуют только `agent` и `subagentStatusLine`, а правила в SKILL.md — это инструкция, а не защита. Поэтому изоляция держится на механизмах уровня ОС и хуков:

- **Образец на диске** хранится без исполняемого расширения (`sample/<sha256>.bin`) и с правами NTFS, запрещающими исполнение. Исходные имя и расширение — в `case.json`.
- **Обязательный хук `PreToolUse`** (не опциональный) на Bash/PowerShell: блокирует запуск файла из `cases/*/sample/`, снятие запрета на исполнение и попытки ослабить защиту хоста. Хук срабатывает независимо от того, что «решит» Claude.
- **Режим разрешений:** для `malware` — только подтверждение каждой команды; режимы auto и bypass запрещены (фиксируется в инструкции кейса, проверяется хуком).
- **Пути** к кейсам, VM и внешним движкам задаются через `userConfig` плагина, не хардкодятся.
- **Карантин антивируса.** Known-образцы в `cases/` будут изыматься Defender. Рекомендуемое решение для `malware` — отдельная «статическая» VM в роли хоста анализа (сеть только к API Claude), а не ослабление защиты рабочей машины. Образцы хранить в архиве под паролем, распаковывая только внутри изолированной среды.
- **У Claude нет механизма** запустить образец на хосте: нет расширения, нет прав, хук блокирует, подтверждение ручное.

### 4.4. Модель угроз: содержимое образца — недоверенные данные

Строки, ресурсы, имена и декомпилированный код образца — **враждебный ввод**, который Claude читает напрямую. Образец может содержать текст, адресованный ИИ-анализатору (встроенная prompt-инъекция): в июне 2025 Check Point описал PE со строкой-инструкцией для LLM ответить «NO MALWARE DETECTED», увязав это именно с анализом через MCP. Удачная инъекция может подделать выводы отчёта, скрыть поведение или спровоцировать команду.

Меры (снижают риск, не устраняют):
- Инструменты `relab-mcp` **размечают** данные, извлечённые из образца, как недоверенные (отдельное поле/обёртка), чтобы они не смешивались с инструкциями.
- Чтение декомпиляции и строк по возможности делегируется субагенту (из `agents/` плагина) **без доступа к Bash/PowerShell**; наружу он отдаёт только разметку/заметки.
- Любая команда — только с явным подтверждением; авто-режимы для `malware` запрещены (см. 4.3).
- Выводы, опирающиеся на текст из образца, помечаются как гипотезы и подтверждаются динамикой (этап 6), а не пишутся в итог напрямую.

## 5. Архитектура: плагин + Rust-бэкенд

### 5.1. Анатомия плагина

```
re-lab-plugin/
├── .claude-plugin/
│   └── plugin.json          # обязательный манифест (JSON)
├── skills/                  # SKILL.md по этапам (markdown)
│   ├── triage/
│   ├── static/
│   ├── deobf/
│   └── dynamic/
├── commands/                # слэш-команды (markdown)
│   ├── case-new.md
│   └── triage.md
├── hooks/
│   └── hooks.json           # опционально
├── .mcp.json                # объявляет Rust MCP-сервер (relab-mcp)
└── bin/
    └── relab-mcp            # <- Rust MCP-сервер (компилируется отдельно)
```

Разделение ответственности:
- **Плагин (markdown + JSON):** порядок этапов, правила изоляции, промпты, слэш-команды, подключение MCP-серверов.
- **Rust MCP-сервер (`relab-mcp`):** нативные инструменты, которые Claude вызывает как tools (триаж, эмуляция, патчинг, работа с PE).
- **Внешние движки:** Ghidra, angr, capa, Frida, x64dbg — вызываются либо из Rust подпроцессом, либо как отдельные MCP-серверы, объявленные в `.mcp.json`.

### 5.2. Что реализуется нативно на Rust

Эти задачи имеют нативные Rust-крейты или официальные биндинги и выносятся в `relab-mcp` как tools:

- **Каркас MCP-сервера** — крейт `rmcp` (официальный Rust MCP SDK, repo `modelcontextprotocol/rust-sdk`): макрос `#[tool]`, транспорты stdio и streamable-HTTP.
- **Разбор и патчинг PE** — крейт `lief` (официальные Rust-биндинги LIEF): секции, импорты, энтропия, перезапись.
- **Сигнатурный поиск (YARA)** — `yara-x` (движок YARA от VirusTotal, нативно на Rust). Без внешнего бинаря.
- **Дизассемблирование** — крейт `capstone`.
- **Эмуляция** (расшифровка строк, участки кода) — крейт `unicorn-engine`.
- **Ассемблирование** (патчи) — крейт `keystone`.

Итог: этапы **триаж**, **эмуляция** (часть этапа 4) и **патчинг** (часть этапа 7) можно собрать целиком на Rust.

### 5.3. Что оркестрируется снаружи (не на Rust)

Тяжёлые движки не переписываются; Rust/плагин обращается к ним подпроцессом или через их MCP:

- **Ghidra** (Java) — `analyzeHeadless` подпроцессом или готовый Ghidra MCP (ReVa / pyghidra-mcp).
- **angr** (Python) — подпроцесс; деобфускация CFF/BCF.
- **capa** (Python) — подпроцесс; детект возможностей.
- **Frida** — существующий Frida MCP (`frida-mcp` / Ya Frida); биндинги `frida-rust` менее зрелы, рантайм в Rust не тащим.
- **x64dbg** — отдельный GUI-инструмент в VM.
- **Kong** — внешний CLI/LLM-слой, запускается отдельно.

### 5.4. Таблица распределения

| Задача | Где | Как |
|---|---|---|
| MCP-каркас | Rust | крейт `rmcp` |
| Триаж PE (формат, импорты, энтропия) | Rust | `lief` |
| YARA | Rust | `yara-x` |
| Дизассемблирование | Rust | `capstone` |
| Эмуляция (строки) | Rust | `unicorn-engine` |

| Диффинг патчей (`vuln`) | Внешне | ghidriff |

## 6. Стек инструментов

### 6.1. Rust-крейты (бэкенд `relab-mcp`)
- `rmcp` — MCP SDK.
- `lief` — разбор/патчинг PE (LIEF 1.0.0 вышел 2026-07-12; Rust edition 2021, rustc ≥ 1.74).
- `yara-x` — YARA-движок.
- `capstone` — дизассемблер.
- `unicorn-engine` — эмулятор.
- `keystone` — ассемблер.

> Версии крейтов (`rmcp`, биндинги) быстро меняются — зафиксировать актуальные на момент старта сборки, не полагаться на числа из этого документа.

### 6.2. Внешние движки (через subprocess / MCP)
- **Ghidra** + **ReVa** или **pyghidra-mcp**.
- **Frida MCP** (`frida-mcp` / Ya Frida).
- **x64dbg**.
- **angr**, **capa** (Python).
- **Detect It Easy (DIE)**.
- **Kong** — LLM-слой деобфускации.
- **ghidriff** — диффинг версий (профиль `vuln`).

### 6.3. Развилка по готовым комбайнам
- **binary-mcp** (Sarks0) уже объединяет Ghidra + x64dbg.
- **revula** перекрывает Frida, r2, LIEF, YARA, патчинг, распаковку.
- **Решение:** не брать целиком. Писать тонкую обвязку (плагин + `relab-mcp`) и подключать готовые MCP-серверы по мере необходимости. Из комбайнов брать идеи, а не код.

## 7. Структура кейса и форматы данных

### 7.1. Структура

```
cases/<sample>/
├── sample/        # оригинал без исполняемого расширения, права запрещают запуск
├── artifacts/     # дампы, декомпиляция, triage.json, отчёты
├── case.json      # состояние кейса (профиль, этап, хэши, версии)
└── notes.md       # гипотезы, найденное, подтверждённое динамикой
```

Кейсы хранятся **вне** папки плагина и вне `${CLAUDE_PLUGIN_DATA}` (обе переживают не все обновления и могут удаляться) — в рабочей области пользователя, путь через `userConfig`.

### 7.2. `case.json` — состояние и воспроизводимость

Без него принцип воспроизводимости не выполнить. Минимум полей:
- `profile`: `understand | malware | vuln | ctf`.
- `stage`: текущий этап (0–7).
- `hashes`: md5, sha1, sha256.
- `original_name`, `original_ext`: исходные имя/расширение (на диске их нет).
- `tool_versions`: версии `relab-mcp`, Ghidra, capa, правил YARA.
- `isolation`: режим сети VM, подтверждение активного снимка.

### 7.3. `triage.json` — контракт этапа 1

Описывается **JSON Schema** (лежит в плагине, по ней идёт приёмка). Ключевые поля: формат и архитектура; секции с энтропией; импорты; детект упаковщика (источник + уверенность); capa-возможности; YARA-хиты; рекомендованный маршрут. Данные, извлечённые из образца (строки, имена), помечены как недоверенные (см. 4.4).

### 7.4. Формат гипотезы

Правило «записывать только подтверждённое» требует отслеживаемой гипотезы:
- `id`, `statement` — утверждение;
- `source` — откуда (статика / строка / догадка);
- `status`: `hypothesis | confirmed | rejected`;
- `evidence` — ссылка на трассу/лог/дамп, подтверждающие статус.

Имена, записанные в базу Ghidra на этапе 3, несут тот же статус и **не** считаются подтверждёнными до верификации (этап 6).

### 7.5. Маршрутизатор

Правила маршрутизации (какой профиль-инструмент и порядок этапов по данным `triage.json`) **детерминированы и заданы в Rust/конфиге**, а не выбираются LLM на лету. Claude предлагает и подтверждает выбор, но правило зафиксировано и проверяемо. Явные ветки: .NET-сборки (ILSpy вместо Ghidra), установщики (NSIS/Inno), упакованные скрипты (PyInstaller/AutoIt).

## 8. Сборка под Windows

Главная расплата за Rust здесь — сборка нативных зависимостей. Требования и риски:

- **Тулчейн:** MSVC (Visual Studio Build Tools, компонент C++), целевой триплет `x86_64-pc-windows-msvc`. Для 32-битных целей анализа тулчейн сборки сервера это не меняет (сервер 64-битный, анализирует и x86).
- **CMake** — нужен для крейтов, собирающих C/C++ из исходников (`unicorn-engine`, частично `lief-ffi`).
- **Крейты по сложности сборки:**
  - `rmcp`, `yara-x` — чистый Rust, проблем нет.
  - `capstone` — вендорит C, собирается относительно просто.
  - `keystone` — требует сборки C-библиотеки keystone.
  - `unicorn-engine` — собирает unicorn через CMake, самое хлопотное звено.
  - `lief` — тянет `lief-ffi` (через `cxx`); может собирать LIEF из исходников или использовать преднастроенные артефакты (bootstrapping).
- **Рекомендация:** на старте собрать `relab-mcp` только с чистыми/лёгкими крейтами (`rmcp` + `yara-x` + энтропия + `lief` для разбора PE), а `unicorn`/`keystone` подключать позже, когда дойдёт до эмуляции и патчинга. Это снимает основной риск сборки с MVP.
- **Поставка бинаря:** плагин должен содержать уже скомпилированный `bin/relab-mcp` под Windows (или инструкцию сборки), т.к. у пользователя плагина может не быть Rust-тулчейна.

## 9. Компоненты к разработке

То, чего нет в готовом виде и что составляет ценность.

1. **Манифест плагина** `plugin.json` + `.mcp.json` с объявлением `relab-mcp`.
2. **Rust MCP-сервер `relab-mcp`** на `rmcp` — каркас и tools.
3. **Инструмент `triage`** в `relab-mcp` (LIEF + yara-x + энтропия) → `triage.json`.
4. **Маршрутизатор** — по `triage.json` выбирает профиль-инструменты и порядок этапов.
5. **Skills по этапам** (`SKILL.md`) — чтобы Claude шёл по шагам и не терял контекст.
6. **Слэш-команды** — `/case-new`, `/triage` и т.д.
7. **Цикл верификации** — «гипотеза из статики → проверка в динамике → запись в Ghidra» с сохранением доказательств.
8. **Память кейса** — структура папок и `notes.md`, переживающие перезапуск.
9. **Модули деобфускации** — подключаемые обработчики под тип защиты (обёртки над angr/unicorn).
10. **Обёртки-оркестраторы** — вызов Ghidra headless, capa, ghidriff из Rust/skills.

## 10. Критерии приёмки (MVP)

MVP = устанавливаемый плагин + Rust MCP-сервер с одним рабочим инструментом триажа, профиль `understand`, Windows-PE.

**Тестовый набор — только безопасные PE:** свои сборки x86/x64 и DLL, своя сборка под UPX, подписанный системный файл, намеренно испорченные файлы. Живого вредоноса в репозитории и CI нет.

- [ ] Плагин ставится через marketplace (`/plugin install`), `claude plugin validate --strict` проходит.
- [ ] `relab-mcp` собирается под Windows (на лёгких крейтах) и объявлен в `.mcp.json`.
- [ ] `triage.json` проходит валидацию по JSON Schema на каждом файле тестового набора.
- [ ] На испорченном PE инструмент возвращает понятную ошибку и **не роняет сервер** (таймаут и лимит памяти соблюдены).
- [ ] Headless-экспорт из Ghidra работает, функции и строки попадают в `artifacts/`.
- [ ] Демонстрационный сценарий: на фиксированном бинаре Claude читает проект, переименовывает функции и пишет гипотезы в `notes.md` в формате 7.4.
- [ ] **Изоляция подтверждена механизмами, а не декларацией:**
  - [ ] права на файл образца запрещают исполнение;
  - [ ] хук `PreToolUse` блокирует попытку запуска файла из `sample/` (есть тест);
  - [ ] в коде `relab-mcp` нет пути, запускающего файл образца.
- [ ] Хотя бы один skill (triage) и одна команда (`/case-new`) работают end-to-end.

Дальнейшие итерации: распаковка (этап 2), эмуляция и патчинг на Rust (unicorn/keystone), деобфускация (этап 4), динамика и верификация (этапы 5–6), профили `malware` / `vuln` / `ctf`.

## 11. Ограничения и риски

- **Сборка нативных крейтов под Windows** (`unicorn`, `keystone`, `lief-ffi`) — главный технический риск; снимается поэтапным подключением (раздел 8).
- **VM-протекторы** (VMProtect, Themida) автоматизации не поддаются — только ручной разбор с ассистированием Claude.
- **Отправка кода во внешний LLM.** Kong и Claude-MCP передают декомпиляцию в облачный API — не прогонять чужие/закрытые бинарники без разрешения.
- **Стоимость токенов.** Автоматический проход на большом бинарнике может быть дорогим; для `understand` ограничивать Kong.
- **Зрелость экосистемы.** Rust MCP SDK и часть биндингов активно меняются; молодые MCP-серверы проверять перед включением.
- **LLM и обфускация.** Модели сами плохо справляются с обфускацией (особенно instruction substitution и комбинации), поэтому деобфускация возложена на детерминированные инструменты, а не на Claude.
- **Prompt-инъекция из образца.** Содержимое образца (строки, декомпиляция) — недоверенный ввод и может содержать инструкции для LLM. Меры — в разделе 4.4; риск снижается, но не снимается.
- **Лимит вывода MCP.** Ответ инструмента ограничен ~25k токенов по умолчанию (`MAX_MCP_OUTPUT_TOKENS`); триаж/выгрузка большого бинаря туда не влезут. Инструменты отдают сводку + путь к полному файлу и поддерживают постраничную выдачу; долгие операции (headless-анализ) — фоновые задачи «запуск → статус → результат».
- **`frida-rust` незрелый** — динамику не тащим в Rust, а оркестрируем через готовый Frida MCP.
- **Поставка бинаря.** Пользователю плагина нужен готовый `relab-mcp` под его платформу; кросс-сборка/релизы потребуют отдельного внимания.
